# [B-004] Crear el flujo web inicial

## Resumen

Conectar la interfaz existente con `POST /api/v1/pieces` (B-003.2) para que el usuario pueda seleccionar un MIDI desde Next.js, enviarlo al backend y ver sus metadatos o un error claro, cerrando el primer flujo completo web → API.

## Objetivo

Que la carga deje de ser una llamada de curl y pase a ser una experiencia real: el usuario elige un archivo, la web lo valida de forma orientativa, lo sube, muestra lo que el backend persistió y explica cualquier fallo sin romper el resto de la página.

## Sub-issues

- [B-004.1 — Crear el cliente HTTP tipado del frontend](B-004.1.md)
- [B-004.2 — Conectar la pantalla de carga y mostrar los metadatos devueltos](B-004.2.md)
- [B-004.3 — Manejar errores de carga y verificar el flujo end-to-end](B-004.3.md)

## Alcance

- Crear `frontend/src/lib/api-client.ts` como único punto de llamadas REST hacia FastAPI.
- Tipar en TypeScript los contratos ya definidos en Pydantic (`PieceResponse`, `PieceMetadata`, errores `code`/`message`); el backend sigue siendo la fuente de verdad del contrato.
- Conectar el componente existente `MidiUploader.tsx` (hoy placeholder) al cliente HTTP.
- Validación orientativa en cliente (extensión y tamaño) que no sustituye a la del backend.
- Estados visibles de la carga: seleccionando, subiendo, listo y error.
- Mostrar metadatos devueltos: título/filename, tamaño, extensión, pistas, duración y número de notas cuando estén presentes.
- Manejar los códigos estables del backend (400 `validation_*`, 500 `persistence_error`) y la caída del servicio.

## Fuera de alcance

- Parsing o normalización de notas en el frontend (B-005 lo resuelve en backend).
- Reproducción y piano virtual (B-006 y B-007).
- Sesiones de práctica y WebSocket (B-012 creará `websocket-client.ts` y `PracticeSession.tsx`).
- Selección del catálogo de piezas (B-027.3).
- Autenticación, paginación o listado histórico de piezas.

## Criterios de aceptación

- [x] Un MIDI válido seleccionado en la web se sube y la interfaz muestra sus metadatos.
- [x] Un MIDI inválido se rechaza mostrando el mensaje del backend, sin excepciones ni pantalla en blanco.
- [x] Todas las llamadas REST pasan por `api-client.ts`; ningún componente usa `fetch` directo.
- [x] Los tipos del cliente coinciden con `schemas.py` del backend.
- [x] La página sigue funcionando si el backend no está arrancado (error controlado).
- [x] El healthcheck y los flujos existentes en verde, y `npm run build` compila sin errores.

## Dependencias

Depende de **B-002** (contrato de piezas) y **B-003** (endpoint con persistencia). Es prerequisito de **B-007** (piano virtual), **B-027.3** (catálogo en frontend) y **B-012** (sesión de práctica sobre este cliente).

## Compatibilidad con otras issues

- **B-003 (endpoint):** consumidor puro; el frontend no reimplementa validación ni persistencia.
- **B-012 (WebSocket):** reutilizará `api-client.ts` y su manejo de errores; B-004 no crea el cliente WebSocket.
- **B-027.3 (catálogo):** añadirá una lista de piezas seleccionables; B-004 solo deja la carga manual conectada.
- **Componentes existentes:** `PianoKeyboard.tsx` y `SessionStatus.tsx` quedan intactos; B-004 no llena su lógica.
