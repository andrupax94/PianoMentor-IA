# [B-012.8] Chat del agente: function calling, memoria y panel

**Estado:** pendiente; documento inicializado, sin implementar. **Entrega objetivo: 2026-10-19.** Adelanta la pieza compartida de **B-012.6** (que sigue abierta y no se cierra).

## En palabras simples

Hasta ahora el agente es una tubería sin cara: existe la sesión (B-012.1), pero no hay nada con lo que hablar. Esta sub-issue pone **el chat**: un cuadro donde el estudiante escribe «pon el minueto de Bach» o «pausa» y el agente responde y lo hace.

El chat funciona con una **lista cerrada de órdenes** (las «funciones») que el modelo puede elegir, y cada una hace algo que **ya existe**: buscar en el catálogo, mandar la pieza al piano, pausar, abrir una sesión de práctica. El modelo solo *elige* la función y redacta la respuesta; no toca el piano ni el motor musical. Si le pides algo que no está en la lista, responde que no puede y dice qué sí puede hacer: eso es justo lo que se quiere demostrar de un agente honesto.

El chat tiene dos formas: en la página del piano se queda **donde siempre ha estado**, en el panel del mentor; en las demás páginas aparece como **panel flotante**. Y recuerda los últimos mensajes de la conversación (memoria a corto plazo), así que se puede decir «pon el minueto» y después «ahora pausa».

## Descripción

Poner cara y voz al agente ya planificado en B-012.6 (proveedor LLM) sobre las capacidades implementadas hasta hoy, con lista blanca de funciones, fallback explícito cuando la orden no existe, memoria a corto plazo y panel de chat en la interfaz.

## Alcance

Cuatro bloques, en este orden; A y B son backend y se pueden cerrar sin tocar la interfaz.

### Bloque A — Registro de funciones, endpoint y memoria (sin LLM real)

- `backend/src/piano_mentor/tools.py` (nuevo): registro de funciones con `name`, `description` (en español, que es lo que lee el modelo), `parameters` (JSON Schema), `side` (`server`/`client`) y `handler` (solo servidor).
- `backend/src/piano_mentor/llm.py` (nuevo): interfaz `LLMProvider` (`chat(messages, tools) -> {text, tool_call}`) y **`MockProvider`** determinista (reconoce patrones: «pausa», «reproduce/pon X», «abre práctica», «qué puedes hacer»).
- `backend/src/piano_mentor/chat.py` (nuevo): orquestación de un turno — historial + contexto → proveedor → validación contra la lista blanca → ejecución de funciones de servidor o devolución de la acción de navegador → redacción final. Bucle acotado (máximo 3 pasos).
- `POST /api/v1/agent/chat` en `api.py` con sus modelos en `schemas.py`.
- Migración `0006_add_chat_messages.sql` y helpers de chat en `database.py` (guardar y leer la ventana de la conversación).
- Códigos estables: `invalid_chat_payload`, `unknown_tool`, `tool_failed`. Los errores de una función **no rompen el turno**: se devuelven al modelo como resultado y él explica qué pasó.

### Bloque B — Proveedor real: Groq, Gemini y LangGraph fino

- Un solo proveedor **compatible con OpenAI**, parametrizado por `base_url`, `api_key` y modelo. Groq (`https://api.groq.com/openai/v1`, `openai/gpt-oss-20b`), Gemini (`https://generativelanguage.googleapis.com/v1beta/openai/`, familia Flash) y la inferencia de OpenCode (`https://opencode.ai/inference/openai/v1`) hablan el mismo dialecto, así que **elegir proveedor es configuración, no código**.
- *Tool calling* confirmado por documentación en los tres. Groq: `openai/gpt-oss-20b` lo soporta, pero **no** las llamadas en paralelo, de ahí una función por turno. Gemini: `tools` con `tool_choice: "auto"` en su capa compatible con OpenAI; esa capa está en **beta** y los modelos 3+ no permiten apagar el *thinking*, así que se pide esfuerzo bajo para no pagar latencia en el chat. OpenCode: mismo dialecto OpenAI, con clave de service account.
- `FallbackProvider`: cadena configurable — por defecto **Groq → Gemini → Mock** —. Si el proveedor elegido falla, se pasa del tiempo o no hay clave, se cae al siguiente y la respuesta se marca con `used_fallback`. El último es siempre el `MockProvider` determinista, que no depende de la red.
- LangGraph **fino**: un grafo de dos nodos (`agent` → `tools`) con `bind_tools` y una arista condicional de vuelta, usado **solo** para orquestar el chat. No toca `note_on`, ni el reloj, ni la reproducción: eso sigue siendo del motor determinista.
- Configuración en `config.py`: `llm_provider` (`mock` por defecto, para que CI y desarrollo sean herméticos), el modelo de cada proveedor, `chat_memory_window` y `llm_timeout_s`. Claves en `.env`: `GROQ_API_KEY` y `GEMINI_API_KEY` (gratuita en AI Studio); `OPENCODE_CONSOLE_TOKEN` solo si algún día se usa su inferencia. Imports pesados en perezoso dentro de cada proveedor, para que el camino de `MockProvider` funcione aunque falte una dependencia.
- Tests: `MockProvider` en CI sin red; el proveedor real detrás de `@pytest.mark.integration` (manual).

## Decisiones

### 1. Esto no es RAG, es *function calling*

RAG sirve para buscar en un corpus de conocimiento. Aquí lo que hace falta es que el modelo **elija entre funciones conocidas**, y para resolver «pon el minueto de Bach» basta con `buscar_pieza` filtrando el catálogo (16 piezas) de forma determinista. No se añaden embeddings ni base vectorial: el premio no compensa el trabajo, y `sqlite-vec` sigue aplazado donde estaba.

### 2. Lista blanca cerrada y respuesta honesta

El modelo **propone**, no ejecuta. Toda propuesta pasa por el registro: si la función no existe, no se ejecuta nada y el agente responde que no puede y recuerda qué sí puede hacer. Es la comprobación de que el sistema no alucina capacidades, y también el criterio de aceptación del proyecto (las acciones del agente son estructuradas y validadas).

### 3. El LLM propone, el backend valida, el navegador ejecuta

Las funciones se parten en dos lados y eso fija la frontera arquitectónica:

- **Servidor** (leer catálogo, estado): las ejecuta el backend, que ya tiene la base de datos.
- **Navegador** (reproducir, pausar, abrir práctica): el backend **solo devuelve la intención** y la ejecuta el front, porque el transporte y el piano viven en el navegador y el backend no debe repartir audio ni MIDI.

Así el motor musical determinista sigue aislado de FastAPI y del LLM, como exige la arquitectura.

### 4. Memoria a corto plazo en SQLite

La conversación se guarda en `chat_messages` y se envía al modelo una **ventana rodante** de los últimos mensajes. Se persiste en SQLite por la misma razón que el estado de sesión: sobrevive a una recarga del navegador, que es lo que hace el estudiante. La tabla es un log *append-only*, sin claves foráneas, como el resto del esquema.

### 5. LangGraph fino, solo para el chat

Se usa un grafo de dos nodos para el bucle agente↔herramientas. Es la «orquestación de alto nivel» que ya anunciaba `architecture_base.md`, y es coherente con que **B-012.6** siga siendo quien haga la máquina de estados pedagógica: LangGraph aquí no decide nada sobre música y no maneja ni un `note_on`. El estado autoritativo de la conversación sigue siendo SQLite, no el *checkpointer* del grafo.

### 6. Reparto con B-012.6

B-012.6 («Groq + salida estructurada») tiene las mismas piezas compartidas que esta sub-issue necesita **ahora**, pero está bloqueada detrás de la evaluación y las reglas (.2 a .4). Por eso aquí se **adelanta** el proveedor y el fallback, y B-012.6 queda para lo suyo: proponer acciones **pedagógicas** (`give_hint`, `slow_down`, `demonstrate`…) contra el estado de la sesión, reutilizando esta interfaz. Ninguna de las dos cambia de alcance; la duplicación se evita diciendo quién posee qué.

### 7. Panel híbrido: un solo chat, dos montajes

El diseño original de la página principal ya reserva el sitio del chat en el `MentorPanel` (armazón estático de B-006.4 desde entonces). Se respeta: allí el chat **se queda** en su columna. Solo cuando no hay piano a la vista (Library, práctica) aparece el panel flotante, y es el mismo componente. Menos código que dos chats y una sola historia que contar.

### 8. Cadena de proveedores: Groq → Gemini → Mock (y OpenCode, documentado)

Groq es el proveedor inicial previsto y su `openai/gpt-oss-20b` soporta *tool calling*. Como su API es **compatible con OpenAI**, añadir Gemini —o la inferencia de OpenCode— es configuración, no código: mismo dialecto, otra `base_url`, otra clave. Gemini tiene además **capa gratuita** (la clave de AI Studio no cuesta nada y los modelos Flash son gratuitos; los límites reales los marca AI Studio por proyecto, no una tabla fija), así que es un respaldo barato para la demo. Dos avisos comprobados o documentados: la capa compatible con OpenAI de Gemini está en **beta** y sus modelos 3+ no permiten apagar el *thinking*; y el nivel gratuito de OpenCode **no** vale desde un backend — probado el 2026-10-17, responde **403** («OpenCode's free tier can only be used from within OpenCode»), luego usar su inferencia exige una *service account key* con presupuesto. El respaldo **garantizado** es, por tanto, el `MockProvider` determinista: sin red y sin clave, la demo no se cae aunque fallen todos los proveedores.

### 9. Una función por turno

`openai/gpt-oss-20b` no admite *tool calls* en paralelo. El diseño lo asume: una función por turno y un bucle corto con tope, que además es lo más fácil de explicar en la demo.

## Contrato

```jsonc
POST /api/v1/agent/chat
{
  "chat_id": "6f1c…",            // opcional; si no llega, el backend crea uno
  "message": "pon el minueto de Bach",
  "context": {                    // opcional; el front cuenta dónde está el usuario
    "page": "/library",
    "piece_id": "p03",
    "session_id": null,
    "transport": "stopped"        // playing | paused | stopped | null
  }
}

200 OK
{
  "chat_id": "6f1c…",
  "reply": "Vale, cargo el Minueto en Sol de Bach y lo reproduzco.",
  "provider": "groq",
  "used_fallback": false,
  "client_action": { "name": "reproducir_pieza",
                     "arguments": { "piece_id": "p03", "auto_play": true } },
  "used_tools": [ { "name": "buscar_pieza", "arguments": { "texto": "minueto bach" } } ]
}
```

`client_action` es `null` cuando la orden es solo informativa o cuando no hay función que la cubra; en ese caso `reply` explica qué sí se puede hacer.
