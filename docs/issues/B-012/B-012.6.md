# [B-012.6] Groq + salida estructurada

**Estado:** hecho. `LLMProvider.propose_action(state) -> ActionProposal` implementado en `backend/src/piano_mentor/llm.py` (`MockProvider` determinista, `OpenAICompatibleProvider` —el de Groq/Gemini— con JSON estructurado y esquema de params derivado de los límites de validación, `FallbackProvider` encadenando), `AgentService.propose_action()` en `backend/src/piano_mentor/agent.py` (valida la propuesta y cae a `decide()` si falla o es inválida) y endpoint `POST /sessions/{id}/agent-step` conectado al proveedor de `settings.llm_provider` con la evaluación de la sesión en `backend/src/piano_mentor/api.py`. Tests: 18 en `backend/tests/test_agent.py` (propuesta, parseo de JSON y esquema) y 5 de endpoint en `backend/tests/test_agent_actions.py`.

**Evidencia en vivo** (pieza p16, backend con `LLM_PROVIDER=groq`): sesiones de práctica reales contra `agent-step` devuelven `provider=groq` con acciones válidas (`slow_down`, `give_hint`, `demonstrate`, `wait`), la sesión con precisión 100 % cae al fallback determinista (`all_good → wait`) cuando la propuesta del modelo no valida, y una respuesta cortada por `max_tokens` se descarta sin romper el flujo. **En la web** (puerto 3000) el paso se dispara con el botón «Pedir paso al agente» del componente `frontend/src/components/AgentStepPanel/`, que muestra acción, motivo y procedencia (`runAgentStep` en `frontend/src/lib/api-client.ts`). **Reparto con B-012.8**: esa sub-issue **adelanta** la interfaz `LLMProvider`, el fallback y el proveedor Groq (adaptados a *tool calling* para el chat); al llegar aquí se reutilizan y esta issue añade lo suyo, la salida estructurada de acciones **pedagógicas** contra el estado de la sesión.

## Descripción

Conectar proveedor LLM (Groq) con salida JSON estructurada para proponer acciones; mantener `MockProvider` determinista como fallback.

## Alcance

- Interfaz `LLMProvider` con `propose_action(state) -> ActionProposal`.
- `MockProvider`: devuelve acción fija o basada en reglas simples (para tests/CI).
- `GroqProvider`: llama API Groq con prompt + JSON schema (action + params), parse valida contra whitelist.
- `AgentService` inyecta proveedor vía config (`settings.llm_provider`).
- Fallback: si Groq falla/timeout → `MockProvider` (sin romper flujo).
- Secrets: `GROQ_API_KEY` en `.env` / Docker secret.
- Tests: `MockProvider` en CI; `GroqProvider` marcado `@pytest.mark.integration` (manual).

## Criterios de aceptación

- [x] `MockProvider` funciona en CI sin secrets (reglas deterministas, sin red ni clave).
- [x] `GroqProvider` devuelve JSON válido contra schema (prueba en vivo con `LLM_PROVIDER=groq`: propone `slow_down`/`give_hint`/`demonstrate`/`wait` con params del esquema; la respuesta cortada por `max_tokens` se descarta → `None`).
- [x] Fallback automático si Groq falla (`FallbackProvider.propose_action` encadena Groq → Gemini → Mock; `AgentService.propose_action` cae a `decide()` si la cadena devuelve `None` o la propuesta no valida — observado en vivo: sesión al 100 % → `all_good → wait`).
- [x] Acción propuesta pasa por `agent.validate()` + `validate_action()` antes de devolverse (test: propuesta con `tempo_factor: 5.0` cae al fallback).
- [x] `python -m pytest -q` pasa sin Groq (380 passed).
